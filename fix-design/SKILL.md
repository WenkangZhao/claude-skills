# 设计一个修复

这些规则的代价:一周之内四个修复被测试团队打回来,其中两个打回两次,而那个构建里**每一个已合并的
修复都在**。第一版结论写的是"能复现报告的那个用例就够了",被否掉了——太被动:**修复必须走遍代码能走的
每一条分支,不是 QE 恰好踩到的那一条。**

## 一眼看完

- **先枚举再设计**:入口 × 状态 × 数据形态 × 流程步骤。每一格都设计到,每一格都验证到。
- **修复是代码,否则它不是修复。** 写在提示词/文档里的一句话是补充,它唯一的检验是真模型跑一遍。
- **找到那道缝**:代码能看到同样的输入并确定性地动作的地方——分发、默认值、body、拒绝消息。
- **拒绝消息是模型下一轮要读的。** 它要说清下一步传什么,以及在循环里怎么处理。
- **修用户键入的那条流程**,不是那个失败的步骤。
- **一个前门一行。** 两条路都能到达的行为,在证明之前就是两个行为。
- **钉属性,不钉调用次数**——除非次数本身就是那个属性。
- **复现报告的用例是烟雾测试,永远不是"做完了"的定义。**

## 零、QE 报的一批 bug:先看整批,再设计一个

1. **先分析。** 在提任何方案之前把根因在代码里找出来。**几个任务经常共用一个根因,所以在给其中一个
   设计修复之前,先把整批的标题读一遍**——对着共用根因打一次性补丁,是要返工的活。
2. **确认是开发要修的,把 Activity 设成 `Development`。** 这是"分诊结论是我们的"的信号,和状态不同。
3. **开始修时把 To Do 移到 In Progress。**
4. **Sidekick 的修复,先跑本地 Sidekick 验证**(`sidekick-verify` 第 5 层)。**最好在提交前**,
   这样一次失败的对话直接回到编辑循环。
5. **给用户看 diff、拿到明确许可再提交。**
6. **压住 PR。** 修复是**成批**的,几个任务进一个 PR。**只有那个 PR 真的开出来时,任务才移到
   In Pull Request。**

> **为什么**:QE 一轮对一个 PBI 提了 29 个任务,而且还在来。一个任务一个 PR 会淹掉评审,
> 同时掩盖掉"少数几个根因解释了大部分报告"这个事实。

### ⚠️ 接缝规则(这一条最贵)

> **永远。** 一份 QE 报告要**沿着 QE 走的那条路**复现,**然后沿同一条路验证**——不能只在修复所在的
> 那半边应用上验证。

**我们几乎每个功能都有两半——桌面版和 Command API——它们共用一份存储。QE 会跨过那道缝;
只在一半上跑的单测不会。**

> **一轮里五个任务被"修好"、测试全绿、被 QE 在同一个构建上重开。** 每一个都是修复和它的测试从没
> 触碰过的接缝穿越:
>
> | 缝 |
> |---|
> | API 清掉了一个**它自己设的**消费标志;QE 是从桌面版的 Force Calculate 设的,那条路从不清 |
> | API 的图例替换把 Main 和类型化表配对;QE 是用**另一个命令**改的类型,那个命令根本不写图例 |
> | stop 走的是计算服务(它知道"在飞行中"的运行);桌面版把一批里的大部分排成了服务根本看不到的宿主任务 |
> | 加了一道**运行时**门;QE 的预期是桌面版的**创建时**门 |
> | 另一个仓库里的工具打印 `Name (Alias)`;解析器只匹配 `Name` |

**怎么用**:

- **设计之前**,写下 **QE 驱动的是哪一半**(桌面点击还是 Sidekick 提示)、**哪一半读结果**,
  然后把那道缝**两侧的代码都读一遍**。Sidekick 的报告还要问:**那个提示词模型会生成哪个命令**?
  **经常不是你正在看的那个。**
- **声称"和桌面版一致"之前,去读那个对话框的代码。**
  **一句自信的错话写在工作项上,代价是一整轮重测。**
- **在重开报告点名的那个 QE 构建号上重新验证**,不是"在分支上"。

## 一、先给缺陷分两类,再设计

**在任何修复被设计出来之前**,把两个分类都写进分析里。永远不要只写"这是 bug、这是补丁"。

**轴 1:缺陷住在哪。** 哪一层、哪个组件拥有它。从用户侧看一模一样的两个缺陷,可能住在不同的层、
不同的 owner、不同的发布路径。

**轴 2:什么样的改动能修它。** 行为变更、API 新增、文档注释、recipe、schema 参数、body、提示词
里的一句话。**多于一种是常态,把它们全部点名才是重点。** 一句话报上来的问题,经常同时需要一个 API
字段 + 一个参数 + 一条 recipe,只供了三分之一的修复会被打回来。

**两个轴为什么不是一回事**:在一个仓库里生成的产物,可能走和它旁边的代码完全不同的发布路径。
**分类买到的是发布顺序和重测门槛**:哪些修复随下一个构建就到测试手里、哪些要单独重发、哪些要平台
部署——因此**哪些报告现在根本还测不了**。

> 我们这边的实例:`58942`(tool-engine)要合并 + 工具定义/语料发布之后 QE 才看得到;
> `58941`(iBuildNet)随构建就到。同一个工作项的两半,重测时机差一个发布。

## 二、枚举,然后才设计

> **永远。** 设计修复之前,把表写出来:**谁**能到达这个行为(每个调用方、每种模式、每个共享同一份
> 存储的域)、在**哪些状态**下、带**哪些数据形态**、跨**流程的哪几步**。**每一格背后的代码都读一遍。**
> 然后设计成每一格都对,并且每一格都验证。

| 轴 | 意思 |
|---|---|
| **入口** | 每个调用方、每种模式、每个前门 |
| **状态** | 有没有打开视图;各种选中;数据存在/不存在/是另一种类型;结果合并还是按实体;操作在跑/排队/已完成 |
| **数据形态** | 一行一个值还是两个;填充还是文字;传的是 id 还是名字还是显示名 |
| **流程步骤** | 创建、计算、轮询、读取 |

**为什么**:复现报告的那个用例,只能确认测试已经找到的那个回归。**它找不出下一个,而下一个报告
永远是隔壁那一格。**

- 一个修复在一条路上做了并且在那里真跑验证过;**隔壁那个 tool body 只读了视图**。
- 一个发了五种文件格式;测试那张"类型 × 格式"的二维表,以及"颜色写成文字而不是填充",是从没画过的格子。
- 一个处理了"给了 id"和"没给 id",从没处理"没给 id 但工程里有一张映射表"。

**怎么用**:**表在第一次编辑之前写下来,并且跟着修复一起贴出去。** 报告的那个用例是它的一行。
某一格在这里验证不了(需要你没有的栈、或者不存在的夹具),**点名说出来**,不要让那一行读起来像"覆盖了"。

## 三、修复是代码,否则它不是修复

一个修复的效果如果取决于"模型会不会照着提示词/recipe/工具描述里的一句话做",**那句话就是补充**。
真正的修复是那段**让这句话变得不必要、或者让忽略它变得不可能**的代码。

指导语仍然保留,但它**唯一的检验是真模型跑一遍**。一个字符串断言只证明那句话存在,不证明它起作用。

**为什么**:每一个住在 API 里的修复都守住了;每一个住在一句话里的修复都回来了。最尖锐的一次:工具描述
从第一轮就写着"把请求原样传过去",模型照样重写了它,300 个只建了 15 个。

**怎么用**:对表里每一格问一句——**模型做错事的时候,代码做什么?** 如果答案是"那就错了",这一格没修好。

> 我们这边的实例:`117614`(ACO 自己挑了 BS 源没问用户)。工具**会**问,但只在参数为空时;模型
> 从不留空。**在 skill 里叮嘱模型"不确定就留空"是一句话,不是修复**——orchestrator 自己的注释
> 就写着"instructing the model to ask first was tried three times and ignored every time"。

## 四、找到代码能强制执行意图的那道缝

一个看起来"属于模型"的行为,去找那个**代码能看到同样输入、并且能确定性动作**的地方:转发查询的
**分发**、字段为空时命令套用的**默认值**、一次调用落成的 **body**、一条拒绝携带的**消息**。

**为什么**:分发同时看得到用户原话和模型改写后的查询,所以它能把用户自己的措辞挂到每一个下游调用上,
不管模型写了什么。创建命令看得到工程的资源池,所以规格没点名时它能自己绑上。tool body 看得到活的
选中项。**这些都不需要模型配合。**

**怎么用**:在设计里**点名那道缝**——"enforced at &lt;分发 | 默认值 | body | 拒绝&gt;"。
没有这一行的设计就是"只有指导语",并且要说出来。

**一个代替界面规则的检查,必须读界面自己那条路(含 fallback),并且和它共用同一段计算。** 一次守卫
锚在"某个默认文件发没发"上,于是拒绝了配置窗口实际提供的 16 种组合,因为窗口在文件不存在时会转换当前
的表。标准是"窗口会写出什么"时,**从窗口的代码推导这个检查,并让校验方和写入方共用那段计算,这样两者
不可能不一致**。**一条规则两份实现,那份实现本身就是缺陷**,不是它产生的那次不一致。

## 五、拒绝消息是模型下一轮要读的

一条拒绝要说清:**什么错了、该传什么、以及在一个遍历很多项的循环里怎么处理这种情况**——哪个查询能列出
备选,以及循环是**逐项 catch** 的,所以一次拒绝只占报告里的一行。

**为什么**:一份记录里模型照着拒绝的提示做了,然后就通过了。另一条拒绝列出了备选却没说循环,于是一次
遍历所有项的扫描**死在第一项上,后面全部没有报告**。

**怎么用**:为"下一轮会照它行动的那个读者"写,而且那个读者可能正在循环里。**把文案当成修复的一部分来测。**

## 六、修用户键入的那条流程,不是那个失败的步骤

复现的单位、设计的单位、验证的单位,都是**用户写下来的那整个请求**,每一步,按顺序。**失败的那一步是
开始读的地方,不是停下来的地方。**

**为什么**:"全部创建、全部计算、在两个点全部读取"失败了三次,每一轮都往下游多走一步:先是计算被挡住,
然后排队的那些读成"从没开始",然后按实体读被拒绝。**每个修复都只在它修的那一步上被验证过。**

**怎么用**:在带着修复的构建上、用用户用的那个模式,**把整条流程端到端跑一遍**再把活交回去,并把记录
贴到工作项上。

## 七、一个前门一行

一个行为能从多个入口到达时——两种聊天模式、一个 API 和一个 UI、桌面路径和服务路径——**在证明之前它们
就是不同的代码**,经常在不同的仓库里,各有各的默认值和 fallback。"产品"做什么的修复,**每个门在表里占一行**。

改描述或改 schema 还要查**消费方实际看到的是哪一份描述**,因为 fallback 路径经常自带一份过期的副本。

**为什么**:一个修复从一个门过了、从另一个门挂了。另一个修复反过来。同一个请求一条路建了 300 个,
另一条建了 15 个。

> 我们这边的实例:`117603` 修了 `create_optimisation_config` 和 `list_optimisation_configs`
> 两个门,**漏了 `get_project_state` 和 `select_objects`**——而那两个才是模型最先走到的门。

## 八、钉属性,不钉调用次数

测试断言的是**修复保证的那个属性**("没有任何一次写入带上了流量"、"那份拷贝是带着映射表写的"),
而不是某个协作者被调了几次。

**除非次数本身就是那个属性。** 修复是关于**代价**的时候,每次操作调几次正是那个保证,钉它是对的。
这是同一条规则,不是例外:**钉修复承诺的东西。**

**为什么**:一个"恰好收到一次"的断言对某个类型失败了,因为它的创建会写两次定义(先默认再填充)。
**修复是对的,测试是错的**,而读者会去二分那个修复。

## 九、复现只是烟雾测试

在报告人的工程和提示词上复现一次,是为了**读那次失败**。它是表里的一行,**永远不是"做完了"的定义。**

> 这一条的第一版把它写成了"做完了"的定义,被用户否掉:*"you will never know QE's project,
> unless they found the regression."*

## 相关

- `debug-root-cause` —— 先把原因证出来;这一份接着回答"修复长什么样"。
- `fix-review-comments` —— 同一套读法用在评审意见上(输入形态表、包住编辑点的构造、辩解句检查)。
- `sidekick-verify` —— 改了模型会读的东西(语料、工具描述、skill)怎么证明它真的起作用。
- `mutation-verify` —— 证明新测试撤掉修复会红。
- `review-standard` —— 别人会用什么尺子量这个修复。
