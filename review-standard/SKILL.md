# 评审的判定标准

怎么看、按多重的力度压、以及一次仔细的评审仍然会漏掉什么。**怎么写出来、怎么发**在
`pr-review`;**收到意见之后怎么修**在 `fix-review-comments`。

## 为什么这一份值得单独存在

我们 PR 上那些带 `<!-- pr-review-pipeline:…:finding:N -->` 的评论,是一个本地跑的自动评审
流水线发的。它的提示词里有一句:

> Read the configured review rules from `{review_rules_path}` before judging.

**那份 rules 就是这份标准的原文。** 所以这不是"一种评审风格",是**我们被判定时用的那把尺子**。
自审时按它走,提前看到的就是它会提的。

---

## 一眼看完

- 正确性是标准。**记录在案的决定是证据,只有用户的裁定才是权威。**
- 评审单位是函数;**行为单位是"这次调用 + 它的实参值"**。
- **只写发现,不写优点。** 没有 PRAISE 这一级,聊天总结里也不写"做得好的地方"。
- 前一次评审**不缩小**这一次的范围。每次都对着 merge base 重看整个 diff。
- diff 里新引用的每个类型/方法,**打开它**。
- 新缓存答不出"怎么失效",它就是一个陈旧状态 bug。
- 你想否掉的发现,是**交给用户的决定**,不是你自己吸收掉的残留。
- **修复方案和发现一样要验证。**
- **一条假注释比没有注释更糟**,它能把 BLOCKER 洗成 NIT。

---

## 一、五个维度

每次评审五个都要覆盖。它们的作用是拦住"评审退化成扫到哪算哪"。

| # | 维度 | 看什么 |
|---|---|---|
| 1 | **方案是否成立** | 真的解决了工作项说的那个问题吗?有没有更简单/更地道的做法?合不合整体架构?有没有范围外的东西,或者该做没做的?**和同target的其它在途改动交叉对一下**冲突与重复 |
| 2 | **性能与资源安全** | 多余分配、装箱、GC 压力;延迟求值陷阱、重复枚举、N+1;泄漏(没 dispose、订阅了不退订);线程安全与 async 阻塞 |
| 3 | **代码质量** | 命名是否透出意图;一个类/方法一个职责;抽象不漏实现;错误被处理而不是被吞;没有魔法数和硬编码字符串;**以及"这复杂度有需求支撑吗"** |
| 4 | **可读性与可维护性** | 新人五分钟能看懂吗?注释讲的是**为什么**还是**是什么**?没有会话上下文的人能不能跟下来?公共面有没有文档注释 |
| 5 | **测试覆盖** | 新逻辑有测试;边界(null、空集合、边界值);测试名字和 arrange/act/assert 结构清楚;**没有把实现钉死的过度 mock** |

## 二、严重度阶梯

**只有这一把梯子**,不要为某次评审发明第二套词。

| 级别 | 含义 | 合并前必须修? |
|---|---|---|
| **BLOCKER** | 正确性 bug、数据丢失、安全漏洞、崩溃 | 是 |
| **CRITICAL** | 严重性能/内存问题、错误处理坏掉、核心逻辑无测试 | 是 |
| **MAJOR** | 违反已确立的设计原则、命名差、危险的并发写法 | 强烈建议 |
| **MINOR** | 风格不一致、小的可读性问题、可改进点 | 有更好 |
| **NIT** | 纯偏好、纯外观 | 作者自己定 |

**没有 PRAISE 这一级,也没有"做得好的地方"这一节。** 上一版标准有,用户明确取消了:四次评审里
优点写到七到十条,占了评审长度和聊天长度,而这些优点从来不会发给作者。验证一个说法成立仍然是工作的
一部分——只是**不写成表扬**。它影响了某条发现就写进那条发现里,其余的写进"没有本地验证的部分"。

**emoji 的规矩分两处**,别搞混:
- **归档的评审文件里不带 emoji** —— 纯文本标签才能被搜索。
- **发到 PR 上的评论可以在严重度词前面带一个图标**(我们现在就是 `🟠 **CRITICAL — …**`),
  让人在一堆线程里扫得动,词本身不变,所以不影响搜索。

NIT 有量上限:**一次评审最多 5 条**,多出来的只在总结里报个数。

## 三、定级校准

严重度不只由代码决定,还取决于**出处**和**触发条件有多可信**。

| 情形 | 怎么定 |
|---|---|
| **既有问题**(这次改动之前就有) | **降一级**,除非这次改动让它更糟,或者顺手修正好 |
| **理论问题**(需要不寻常条件) | **降一级**,除非那个条件在生产里可信。判据:**代码库自己是不是已经约束掉了这个场景**——"一个目录里两个文件"在一个规范地一目录一文件的产品里就是理论问题 |
| **新的非平凡逻辑没有测试** | **CRITICAL** |
| **只是搬了位置、逻辑没变的代码没有测试** | **MINOR** —— 它在原处已经被测过 |
| **测试代码卫生**(临时目录没清、少个 try/finally) | **MINOR**。测试产物本来每次重建。只有能证明它污染并行或后续测试才升级 |
| **对成立的不变量加防御**(刚插入成功后再判 null) | **NIT**。不变量成立,加断言是好事但挡不住真 bug。只有当有记录在案的将来工作会打破它才升级 |
| **文档注释缺失** | 只对**公共面**提。summary 描述了会抛但没写类型,**升一级**——调用方需要知道 catch 什么。私有的、显而易见的,**不提** |

## 四、不要提的

- 项目没有确立成约定的风格偏好
- "我会用另一种写法",却没有具体的改进
- 已经很直白的代码还要求再抽象
- 显而易见的代码要求补文档

## 五、十条判断规则(最值钱的部分)

每条后面那句"出事经过"是它存在的原因,别删。

### 1. 正确性是标准

对着"什么是正确"判,不是对着"谁写的"或"之前定过什么"判。**记录在案的决定是关于意图的证据,
不是对正确性的权威。** 唯一的权威是用户的明确裁定——用户定了的,就不再翻案。

### 2. 读代码,不只读 diff

diff 回答不了"这个成员干什么"和"谁在调它"。**把分支检出来读。**

用**一个**长期存在的评审检出目录,专门干这个。不要一次评审开一个 worktree——一个新 worktree
可能是几万个文件,一个就够。因为那里没有用户的东西,`git checkout -f` / `reset --hard`
在**那一个目录里**是安全的;这个许可**不传递到任何其它检出**。在那里**永远不要 `git stash`**
——stash 栈是所有 worktree 共享的。

### 3. 审接缝,不审函数

**至少有一遍要顺着"值"和"事件"走完整条链,而不是按文件切。** 按文件切评审,恰好毁掉这类缺陷赖以
存在的信息。

> **出事经过**:一次抽取改动,三轮评审、其中两轮是逐行的多 agent 评审,两轮都得出"行为一致"。
> 两个 bug 都能轻易复现。四个结构性盲点:
>
> 1. **机制验了,接线没验。** 那个检查确实是逐字照搬的,但**没人验证每个调用点喂给它的实参**:
>    一个是越界**读**填充值,legacy 那个是计算**写**入的哨兵值。评审单位是函数;行为单位是
>    "调用 + 值"。
> 2. **负空间。** legacy 的 try/catch 骨架**本身就是行为**(catch、返回 null、渲染空白)。
>    逐行评审只验证存在的行,**少掉的 catch 是看不见的**,除非先把 legacy 骨架抄下来逐条打勾。
> 3. **没有 legacy 对照物 = 没有比较。** 新加的机制(一个 reader 缓存)落在"对齐"这个框之外,
>    于是"忠实吗"悄悄变成了"自洽吗"。它真正的义务是透明性不变量:**命中必须等于重新解析一次**,
>    再加上一份"哪些事件会让它失效"的清单。改名没有驱逐,没人问。
> 4. **静态评审,时序 bug。** 每一遍都在冻结的存储上追单次读取,真实流程是"算、显示、**改**、重画"。
>
> 外加**测试出处**:对齐测试钉的是实现自己的常量(代码用 NaN 它就喂 NaN),所以它一路绿着还是错的。
> **钉子必须来自 legacy 源码或 legacy 写出来的产物。**

### 4. 不受前次评审锚定

每次评审都**对着 merge base 用新眼睛重看整个 diff**,不管之前评审结论是什么。前一次评审是参考
资料,最多是"从哪里切分评审人"的提示,**永远不是缩小范围的豁免**。

> **出事经过**:一次评审把范围缩到"我上次放行之后的 12 个新提交",跳过了之前的 64 个。另一条
> 评审线在被放行过的提交里抓到一个 BLOCKER(删掉的 null 守卫会静默清空默认列)和一个 CRITICAL
> (项目级生命周期的陈旧缓存)。

### 5. 打开每个新引用的类型

diff 里每一行 new 一个类型、调一个方法、订阅一个事件、注册一个服务——**打开那个类型或方法**,
确认生命周期、副作用、dispose 契约,然后才放行。**内联的 `new Foo(...)` 不是黑盒。**

**验契约,不只验行为。** diff 把调用点指向某个成员时,把那个成员的**可空标注和文档**对着它的
实现、以及对着新调用点的用法核一遍。把 null 传给一个标了非空、而实现恰好能处理的参数,**即使行为
对了也是契约缺陷**——将来有人会把这些调用点"修"成一次行为变更。标注和文档在**同一次改动**里改掉,
零风险。

> **出事经过**:一个泄漏的订阅者挂在静态任务管理器上,把构建卡了一周。作者和评审都把那个构造调用
> 读成"传了个值类型参数"。打开文件就能看到构造函数订阅了三个静态事件、类是 disposable、有个标了
> 非空的字段只在后面某个方法里才赋值。三件事都只差一次点击。
>
> 解释 bug 为什么漏过评审时,**"信息被藏起来了"几乎总是错的**——如果那个类型就在本仓库里。诚实的
> 答案通常是"没人打开那个文件"。别把后者包装成前者。

### 6. 缓存必须有生命周期和失效策略

改动里加了缓存——字典、lazy 字段、memo,任何形式——**放行前书面回答四个问题**:

1. 谁构造那个持有者,多久构造一次?
2. 那个实例活多久?
3. 在它活着期间,什么能改动被缓存的源?
4. 发生时缓存怎么失效?

**第四个答不出来,这个缓存就是错的。**

> **出事经过**:"按 item 缓存 id"看起来是 O(N)→O(1) 的胜利,直到追了归属:那个查找服务构造在
> 另一个服务里面,而那个初始化**每个工程跑一次**。于是字典活整个工程生命周期、零失效,用户增删了
> 被缓存的资源之后它**永远**报陈旧答案。这个优化当时是被**表扬**过的,没人查生命周期。
>
> **顺便查线程安全**:try-get 加 index-set 的普通字典在任何并发下都不安全。要么并发集合,要么
> 明确的单线程契约。

### 7. 扇出是例外,不是默认

**顺序跑一到两个评审 agent,收完一个再开下一个。告诉每个 agent 不要再开子 agent**;验证在主会话
里对着代码做。

> **两边都有出事经过。** 五个并行评审各自再开验证子 agent,**几分钟烧光整个会话额度,两次,几乎
> 什么都没完成**——这是代价侧。收益侧也是真的:一个 263 文件、76 提交的改动上,单遍评审漏掉多个
> 跨文件 bug,而按层切成四个评审人抓到了。所以扇出有用,而且贵到应该**由用户决定**。

**怎么用**:开始前先 `git diff --shortstat` 量一下。超过大约 **50 个文件或 20 个提交**,就说明
扇出会有帮助、大概多少代价,让用户选。**按模块/程序集/层分组,绝不按提交时间顺序**,每个 agent 拿
到端到端的一整片(含与相邻片的交互)。反制条款仍然成立:**必须有一遍顺着值和事件走完整条链**。

### 8. 裁决不是否决权

你想否掉的发现,是**交给用户的"留还是修"的决定**,带着那个便宜的修法一起明确摆出来。它**永远不能**
被折叠进一句"已接受的残留"里。

**对着两个参照裁决:主线 AND 被测分支的基线。** 删掉任何还活着的守卫都是一条发现,即使主线上没有
那个守卫。几条独立评审都指到同一处、而且修法便宜又不影响流程时,**默认就修**。

> **出事经过**:三遍新眼睛评审找到了后来外部评审提的那两个问题。它们在**裁决**环节被过滤掉了,被
> 归进一句"与主线一致,是恢复不是引入"的批量结论里,最后用户在第四次评审说了同样的话之后强制要求修。
> 覆盖率是完整的;丢掉的是一次没被复核的判断。**新眼睛的设置去掉了"发现"环节的作者偏见,但每条发现
> 随后都流经作者做"判定",偏见在那里回来了,而且没有任何东西在把关。**

### 9. 连修复方案一起验证

处理评审有**两个**验证步骤,不是一个。**发现是一个假说,跟它一起来的修复方案也是。** 接受一条正确的
发现、套用它错误的修法,产出的是一个"看起来被评审过、但仍然不工作"的改动。

一轮里同时出现的两种形状:
- **发现对,修法错。** "重着色那条腿写的是第二个颜色字段,而所有 mapper 读第一个,所以重着色后的图
  是空白"——完全正确,是那轮最好的发现。但它建议的值 alpha 是 0,照做仍然什么都渲染不出来。
- **听着对,修法不可能。** "在示例里用临时路径 helper"——那个命名空间在脚本沙箱的禁用名单上,照做
  示例根本编译不过。带着证据拒绝。

### 10. 评审的提问是一次覆盖率检查

评审问"某个交付物落在哪了"的时候,**打开工作项描述,把它点名的每一项逐个对着仓库查**。不要凭记忆
回答"我交了什么"。

> **出事经过**:一句客气的"我猜这些在别处,能确认一下吗"是一次穿着问句外衣的覆盖率检查。评审看不到
> 兄弟仓库也看不到工作项,所以他递给你的正是**你最不适合自己跑的那次审计**。一次改动里评审问了两个
> 交付物的下落。一个没问题。另一个有:工作项描述点名了它,而那个文件里相关词出现 **0 次**,并且它
> 描述的还是更早的一版命令面,因为没有任何东西重新生成过它。三轮评审、两次合并都从它上面走过去了,
> 因为所有人都在查**变过的代码**,而不是**没变的验收文字**。

**怎么用**:评审时重读工作项描述,把它承诺的每个名词列出来,逐个 grep。**生成物最容易被漏**——它
过期时不会有任何东西失败,它只是安静地描述着一个更早的世界。

### 11. 假注释比没注释更糟

> **永远。** 一条断言行为的注释,**必须在写下它的那一刻**对着它所在的那个函数体验证。不是对着设计
> 笔记,不是对着兄弟实现。它说某个成员做 X,就**去读那个成员**。

没有注释会让下一个读者去查代码。**一条自信的注释会让他跳过这次检查**——而"下一个读者"包括几个会话
之后、完全不记得自己写过它的你。

> **最严重的一次:一条假注释把一位仔细的评审说服着放过了一个数据丢失 bug。** 一个网格形状字段被
> 写成"各楼层切片数之和"。它不是那个和——它来自对齐网格的跨度,整跨一次取整,而每层那个字段是每层
> 各取一次整,所以**和通常更大**,并且有两个提交在案的测试断言了这个差。两个后果:一次截断是对着
> 错的字段写的,删掉了读取方仍在寻址的切片,每次重算都把顶楼清空;**一次自动评审检查了那次截断,
> 把那句话当成证据引用,得出"两者只是碰巧相等"的结论,定级 MINOR。** 第二次评审说是必修,是对的。
>
> 所以假注释不只是误导下一个作者——**它会把自己洗成评审证据,把 BLOCKER 变成 NIT。**
> **两次评审对同一行有分歧时,分歧本身就是信号**:去看源码,并且不信任任何"证据是一条注释而不是
> 代码"的结论。

**怎么用**:
1. 行为断言在写下时就对着所在函数体验证。
2. **声称"有测试覆盖"的注释是在断言别的文件的事。** 要么去确认哪个测试真的执行了那条分支,要么
   别下这个断言。更好的做法是把那个测试写出来,让断言成真。
3. **提防"前瞻型"注释。** "随 X 一起退役"、"放在 Y 旁边以免两者漂移"、"推迟到 Z"——X/Y/Z 一变
   它们就腐烂,而且会指着不存在的东西活下去。面包屑应该点名**取代它的那段代码**,绝不点名一张票或
   一个将来的事件。
4. 纠正一条时,**说清楚真相是什么以及为什么**,不只是否定。理由才是防止它再次腐烂的东西。
5. **一个假说法通常存在于不止一处,而提交信息是被忘掉的那一份。** 纠正注释不算完成,除非你把那句话
   的措辞在本分支的提交信息里 grep 过。**没推的历史是免费的。**

## 六、写出来的形状

归档的评审文件:

```markdown
# Review: <change id> - <title>
**Date/Repository/Source/Author/Linked work items**

## Findings
### `<file path>`
- BLOCKER: <描述> (line N)

## Summary
| Severity | Count |

## Not verified locally
<读了但没跑的、复现不了的、以及为什么>

## Verdict
<Approve / Approve with minor comments / Request changes / Reject>

## Recommendations
```

| Verdict | 什么时候 |
|---|---|
| **Approve** | 可以合 |
| **Approve with minor comments** | NIT 处理完就合 |
| **Request changes** | 有 MAJOR/CRITICAL 要先解决 |
| **Reject** | 根本方案要重想 |

**一个 verdict,不是四个空框的清单。** 选一个,用一句话说为什么。

**"没有本地验证的部分"不是道歉,是范围声明。** 读者需要知道"模块 X 没有发现"到底是"干净"还是
"根本没打开"。写清楚:读了什么没跑、什么复现不了、为什么。

**聊天总结**和发到 PR 上的总结评论可以是同一段文字。**先说 verdict 和计数,再说发现。永远不要
以"这个改动做对了什么"开头。**

## 六点五、按栈补读(评审不只是 Command API)

上面六节和栈无关,每次评审都用。**审桌面版和其它仓库时**,再读同目录这两份——它们回答的不是"多严重",
而是**"这算不算违规"**,而这恰恰是"风格偏好不要提"和"已确立的约定必须提"之间那条线。

| 改动落在哪 | 另读 | 它回答什么 |
|---|---|---|
| 任何 C#(桌面版、BLL、SDK、测试) | **`CSHARP.md`** | 大括号、`Assert.That`、`.cs` 的 BOM+CRLF、`global using`、命名,以及我们自己那十条已确立的约定 |
| 新公共类型、跨程序集引用、限界上下文 | **`ARCHITECTURE.md`** | 外部消费方表、放一个新类型、port 谁实现谁消费、什么算泄漏 |
| 参数/依赖/接口的**形状** | **`DESIGN.md`** | 参数收窄、assert vs throw、单实现 port、构造注入、遍历前快照 |
| 重新实现一条 legacy 路径(抽取/迁移/合并) | `extraction-review` | 整链对齐、守卫并集、见证者在契约外、零引用门 |
| Sidekick 语料 / 工具描述 / skill 文本 | `sidekick-verify` | 模型会读的东西,**读过并照做之前都不算验证过** |
| QE 报的 bug | `fix-design` | 修复的形状:枚举每条路、找到那道缝、一个前门一行 |

**两条最容易判错的**:
- **风格**:项目**没有**确立成约定的 → 不要提;`CSHARP.md` 里那些**是**已确立的 → 提,而且不是 NIT。
- **泄漏**:**宿主实现的 port 待在 `Domain.Shared` 是合法的**。把它报成泄漏,是在让作者去挪一个
  规则要求它留下的类型。判之前先确定**谁实现、谁消费**。

## 相关

- `pr-review` —— 审别人的 PR:拉取、逐条核实、发 inline 评论、总结线程。**定级用本文件。**
- `pr-self-review` —— 推之前审自己的 diff。**定级用本文件**,并且因为自动评审读的是同一套标准,
  这里走一遍 ≈ 预判它会提什么。
- `fix-review-comments` —— 收到意见之后怎么改才不会带出新的,含一轮的顺序和逐条 verdict 清单。
- `mutation-verify` —— "证明这条测试真的钉住了这个修复"的执行工具。
