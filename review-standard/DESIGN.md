# 代码形状(评审时判"这个类型/参数/依赖该长这样吗")

审 C# 设计改动时读这一份。`CSHARP.md` 管**写法**,`ARCHITECTURE.md` 管**住哪**,这一份管**形状**。

## 一眼看完

- **函数体把参数 cast 成更具体的类型 = 参数声明太宽。** 在声明处收窄。
- **`Debug.Assert(x != null)` 紧跟着 `x.Y` 是 release 构建的回归。** 不变量在 release 里承重就 `throw`。
- 以"不变量成立"为由删掉守卫,**就要把那个不变量写成 assert**,不是写成注释。
- **只有一个实现、又没有分层或可测性理由的 port,是过度设计。**
- 按领域枚举分派的泛化方法,想变成**每个 case 一个方法**。
- **上下文状态从构造函数进来,绝不从环境查。**
- 一个注册 API 开始返回 disposable 之后,**每个遍历点都要先快照**。
- **用窄 catch 修竞态,不要靠放弃 dispose。**
- 过渡代码带一行面包屑,**点名取代它的那段代码**。

---

## 1. 在声明处收窄参数

方法体如果把参数 cast 成更具体的类型,**参数声明就是错的**。把参数收窄成函数体真正需要的最强类型,
**让 cast 待在调用点**,那里编译器会管。

**为什么**:宽参数**宣传了比函数体兑现的更多的东西**。测试替身和将来的实现会撞上那个 cast,
**在方法深处抛出**。缝上的一次 cast 会在一个已知位置快速失败。

**评审时怎么找**:扫函数体里**把参数 cast 成具体类型**的地方。找到一个,就意味着要改参数类型、
把 cast 推给调用方。

## 2. assert 紧跟解引用 = release 回归

`Debug.Assert(x != null)` 紧跟着 `x.Y` 是一次 **release 构建的回归**:assert 被编译掉了,
所以生产里一旦违反,**下一行就是裸的 null 解引用**——**严格地比它经常取代的那个 `if (x != null)`
守卫更糟。**

不变量在 release 里承重,就 **throw**。一个 invalid-operation 异常诊断信息一样,而且 debug 和 release
行为一致。

> **出事经过**:一个窗体的保存处理器把"带 null 守卫的赋值"换成了"assert 加不带守卫的赋值"。
> 这在评审里**被表扬**为忠实执行了"把不变量编码成 assert"。一条竞争的评审正确地指出:
> **release 构建现在会在下一行挂掉,而不是静默跳过。**

**"用 assert"这条规则的意思是:用 assert 代替一句备注。它不授权把 assert 和一个不带守卫的解引用
组合起来,去替换本来带守卫的代码。**

**怎么判**:按 **release 行为**选。违反必须在生产里响亮,就 throw。
assert-then-dereference 只留给"release 里下一行挂掉确实可以接受"的不变量:
**开发脚手架,绝不用在保存、提交、持久化路径上。**

第二个后果:assert 在 debug 里会收窄可空流状态,所以 **release 构建可能在它下面那一行冒出 debug
从没显示过的 null 解引用警告**。

## 3. 把删掉的防御编码成 assert

以"某个不变量成立"为由删掉防御性代码(CAS、锁、null 检查、校验)时,**把那个不变量编码成 assert 或
前置条件守卫。不要留成文档注释里的一句备注。**

**为什么**:**注释描述意图,并随着周围代码漂移而腐烂。** assert 在不变量破掉的那一刻就触发,
带着违反处的文件和行号。

**怎么用**:被删掉的防御代码附近,每一句"这样是安全的,因为 X",**都是一个"对 X 加 assert"的候选**。
然后套用上一条:**不变量在 release 里承重,就改成 throw。**

## 4. 单实现的 port 通常是过度设计

一个 port 只有在下面至少一条成立时才值得存在:

1. **多实现是真的**——生产加上带替身的测试,或者确实有多个具体来源。
2. **消费方所在的程序集看不见实现的依赖**,所以有分层边界风险。
3. **实现的依赖很重或传递性很强**,而这层间接对消费方有可度量的价值。

**一条都不成立,就塌成最近那个自然程序集里的一个普通类。**

> **出事经过**:一个"默认值 port"被引入 contracts 程序集,理由是"把基于文件的查找挡在上下文外面"。
> 评审把它退回了:**只有一个实现,它唯一的消费方本来就依赖宿主**,而实现的依赖住在宿主里而不是什么
> 难看见的地方。这个 port 带来了容器注册、调用方一次环境查找、和窗体上的**第七个构造函数参数**,
> **没有任何可观察的收益。**

**公共契约面上的单实现 port 是最糟的情况**:它膨胀了契约面,却没给调用方任何直接引用给不了的东西。

## 5. 按枚举分派的方法拆成每个 case 一个方法

服务方法形如 `DoX(kind, ...)` 而 `kind` 是一个**领域枚举的小闭集**时,拆成每个 case 一个方法。

**为什么**:**每个枚举 case 都是它自己的业务概念。** 塌在一起会抹平一个真实的领域区分,
**逼读者在每个调用点解码那个枚举才能恢复语义**。拆开的签名直接带着领域词汇。

**怎么判**:参数叫 "kind"、"type"、"category" 并且取自一个**固定的领域枚举**(相对于开放式数据),
就该拆。**写方法同样适用。**

## 6. 构造函数注入,不要环境状态

上下文状态**从构造函数进来**,绝不通过环境查找拿。

> 我们已有的记忆:`feedback_no_global_state`(避免 `Project.Current`、ThreadStatic、
> 单例服务定位器、`AppConst`;优先构造注入或显式穿参)——同一条规则。

## 7. 注册 API 开始返回 disposable 之后,遍历点要先快照

一个注册 API 一旦开始返回 disposable,**每个遍历点都要先快照一次**,否则在遍历中注销会改集合。

## 8. 用窄 catch 修竞态,不要靠放弃 dispose

竞态用一个**窄的 catch** 修,**不要靠丢掉 dispose** 来绕开。

## 9. 过渡代码带一行面包屑

过渡性的代码带一行注释,**点名取代它的那段代码**。

> **和我们的记忆一致**:`feedback_comments_describe_behaviour` 说注释不写分支名/任务号。
> 这里的规则是一样的:**面包屑点名的应该是取代它的那段代码,绝不是一张票或一个将来的事件**
> ——因为票会关掉而事件会过去,那条注释就指着不存在的东西活下去。
> (`ARCHITECTURE.md` 里 `Transitional\` 目录那条,是用户明确授予的唯一例外。)

## 10. 扩展方法的文档写的是它字面包了哪一次调用

一个扩展方法的文档注释描述的是**它字面上包装的那一次调用**,不是它"大概是干什么的"。
