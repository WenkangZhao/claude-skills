# 修评审意见,而不是把问题越修越多

## 什么时候用 / 什么时候不用

- 用:**动手改第一行之前**;一轮修复之后又冒出新 comment;CI 在你"修好了"之后变红;
  用户问"是不是刚才的改动导致的"。
- 不用:决定哪些意见要修、哪些回绝(那是 `pr-self-review` 的分档);审别人的 PR(`pr-review`)。
  **这个技能只管一件事:已经决定要修了,怎么改才不会带出新的。**

## 先看清事实:不是工具不够,是读法不对

一次真实的三轮统计(PR 58849,2026-09-18):

| 轮次 | 发现数 | 其中由上一轮修复引入 |
|---|---|---|
| 第 1 轮 | 8 | — |
| 第 2 轮 | 4 | 4(全部) |
| 第 3 轮 | 4 | **4(全部,且出现 BLOCKER)** |

条数在收敛,**严重度却在上升**。

关键事实:**评审一次软件都没跑过。** 他没有活的宿主、没跑 pytest、没做 E2E——和作者
完全一样的条件。但那个 BLOCKER(`else` 改嫁,导致任何正常调用都被判"没有目标")、
提示写进了不会被序列化的字段、追问指向了装不下答案的参数——**三条全是读出来的**。

所以"本机跑不了行为测试"**不是借口**。差别在读法:

> **作者读的是:"我改的这条路走通了吗?"**
> **评审读的是:"我没改的那些路,现在会怎样?"**

回归永远在你**没想到的那条路**上。

---

## 第一条(最重要):列出所有输入形态,逐个用手走一遍

评审那条 BLOCKER 的原文,本质上是一张**手算出来的真值表**:

> - `target_dbm: -65` 且没有 `targets` → 在 430-435 行加了 coverage KPI,然后这个条件为假,
>   于是 body 追加"This configuration has no target."
> - `targets: [{kind: "coverage", ...}]` → 这个条件同样为假,同样报错
> - coverage 加 SINR → 同样

他没运行任何东西。他**枚举了输入形态,一条一条走**。我当时只走了自己关心的那一条
(SINR 恢复),它确实通了——另外三条全塌了。

**动作(修完任何带分支的代码之后,强制执行):**

1. 写下**所有**能到达这段代码的输入形态。写不出来,就说明你还不理解刚改的代码。
2. 逐个走一遍,**把每一步的行号和结果写下来**——不是在脑子里过。
3. 做成一张表,**放进提交信息或回帖**。写不出这张表 = 没验证。

```
形态                          走到哪               结果
target_dbm 单独               430-435 加 coverage   ✔ 有目标
targets:[coverage]            420-427 加 coverage   ✔ 有目标
targets:[coverage, sinr]      420-427 加两个        ✔ 有目标
targets:[sinr] + target_dbm   补充分支              ✔ 有目标   ← 我只验证了这一条
targets:[] / 都没给           —                     ✔ 报"没有目标"
```

**这张表如果只有一行是对勾,其余你没填——那就是下一轮的 comment。**

## 第二条:顺着数据往外读,直到它离开系统

改在评审指的那一行 ≠ 用户看到的东西变了。两个真实例子,评审也是纯读出来的:

- **提示写进了没人读的字段**:我把放置区域的提示加进 `notes`,而那条出错路径的信封
  只序列化 `problems` 和 `needs`——评审去读了**信封的代码**(690-695 行),不是我的那行。
- **答案回不来**:我让追问指向 `targets`(对象数组),而表单合并回来的是标量,烘焙成
  **空数组**。评审去读了**烘焙器**,走完了整个往返。

**动作:** 每个修复问两句,并且**去读那段代码**,不是假设:

1. **出口**:我写进去的值,**谁把它发出去**?那条路径真的会执行到吗?
2. **往返**:我让对方回答的东西,**回来的形状**能被读进来吗?追问、选项卡、表单、重试——
   **只验证去程不算验证。**

## 第三条:编辑之前,读完包住它的整个结构

评审指着一行,你改那一行,**你没读它前后**。这一轮三个事故全在这里:

- **`else` 改嫁(BLOCKER)**:在 `else if (…) {}` 和 `else { "没有目标" }` 之间插了一个新
  `if`,那个 `else` 就绑到了新 `if` 上。**合法 C#,编译通过,测试全绿。**
- **变量重名(CS0136)**:外层声明 `var matches`,后面的循环里早有一个 `matches`。
- **改措辞打红自己的测试**:`"re-aiming"` → `"aiming"`,上一轮自己写的断言立刻红。

**动作:** 把包住编辑点的**整个构造**读完——整条 if/else 链、整个方法、整个 using 块;
再 `grep -n "<你要改的标识符或字符串>"` **整个仓库**,不只是评审给的那一行。

## 知道每一种"绿"证明了什么

| 绿 | 证明了 | **没有**证明 |
|---|---|---|
| 解析 / `py_compile` | 能解析 | 任何行为 |
| 编译通过 | 类型能解析 | **控制流**——`else` 改嫁是合法 C# |
| 构建通过 | 能产出程序集 | **测试会不会红** |
| 源码文本断言的测试 | 某段文字在文件里 | **执行路径**——body 全坏它们照样绿 |
| 变异检查 | 这条测试真钉住了这个修复 | 别的没被打破 |
| 手走输入形态表 | **控制流**(评审用的就是这个,零成本) | 真实数据下的数值 |
| 真跑一遍 | 行为 | — |

两条硬规矩:

- **回帖里的证据不能比你实际爬到的那一级高。** 说过一次"8/8 测试通过、COMPILE OK",
  而那 8 条在 body 完全不可用时**照样全绿**。正确写法:"编译通过;测试是源码断言,
  不执行控制流;控制流按下表手工走过。"
- **注意那句"跑不了所以没验证"是不是在偷懒**——上面那张表是免费的,而它抓住了这一轮
  全部三个真缺陷。

## 其余四条(都对应真实事故)

**改动拿掉了某个"恰好成立"的东西 → 先找依赖它的测试。**
把 positions 数组从每 cell 2 个 float 改成 3 个(修复本身对),第二次调用就不再抛越界了;
而那条测试用的是 `Assert.Catch`,**要求必须抛**。CI 红。修复和它的测试要一起改。

**这一轮新写的每条测试,都要变异检查,而且每种还原方式都试。**
两次险些交出不钉任何东西的测试:preflight 那条只断言 `if (preflight)` 的**位置**、不断言
里面的 `return;`;`rindex("if (…)")` 在 `else if (…)` 里**也命中**,所以改回 `else if`
之后测试仍绿——收紧成"它前面那个词不能是 else"才真的红。

**断言贴着被测的块,不要整文件。**
`assert "re-aiming" not in body` 咬到了**我自己解释"为什么不叫 re-aiming"的注释**;
`assert 'Need("targets"' not in body` 咬到了另一处既有的无关分支。先把块切出来再断言。

**没追到症状之前不要 resolve。** Resolve 是在说"这条不用再看了"。两次过早 resolve,
两次被打回(放置区域、SINR 追问)。追不到、或只做了一半,就写清楚**留 active**。

**用不处理转义的方式写代码。** 同一个坑两次:heredoc 里 `'\\n'` 塌成真换行,落进字符
字面量。多行代码用 Write 工具;必须写反斜杠时用 `chr(92)` / `repr()` 注入,或者换个不需要
转义的写法(`ReadAllLines` / `splitlines()`)。

## 每一轮结束前的自检

```
git diff <上一轮的提交>..HEAD      # 只看这一轮自己改了什么
```

1. **输入形态表填满了吗?**(不是只填我关心的那一行)
2. 我插入的每一段,**紧跟其后**是什么?有 `else` / `catch` / `finally` 改嫁给我吗?
3. 我新引入的每个名字,在作用域里唯一吗?
4. 我改掉的每个字符串/异常/分支,有测试依赖它吗?grep 过了吗?
5. 我这轮加的每条测试,变异过吗?每种还原方式都试了吗?
6. 回帖里每句证据对应哪一级?有没有把低级当高级说?
7. 要 resolve 的每一条,**症状真的没了吗**?

第 1 条和第 2 条最高产——这一轮三个事故全被它们覆盖。

## 什么时候停下来

- **严重度回升**(MINOR → BLOCKER):停止编辑,把自己这几轮的 diff 当别人写的从头读一遍。
- **同一个文件连续三轮**:冻结它,除非再出 BLOCKER/CRITICAL。
- **没约定合并线**:不约定,每次全量重读都必然再产出几条 MINOR。和评审约
  (`pr-self-review`):**BLOCKER/CRITICAL 清零;MAJOR 修或挂工作项;MINOR 作者裁量。**

## 陷阱速查

- 只验证"我修的那条路",不验证其他路 —— **这一轮所有 BLOCKER 的来源**。
- 在 if/else 链中间插 `if` —— 后面的 `else` 改嫁给你,而且编译通过。
- 只跑构建就说"验证过" —— 构建绿和测试绿是两回事。
- 拿源码文本断言当行为证据 —— body 全坏它们也绿。
- 把提示写进那条路径不会序列化的字段 —— 用户什么也看不到。
- 把答案指到装不下它的参数上 —— 追问变死循环。
- 修好缺陷,忘了那条靠这个缺陷通过的测试。
- 改措辞,忘了上一轮自己写的、钉着旧措辞的断言。
- 整文件范围的否定断言 —— 咬到自己的注释。
- `rindex("if (…)")` 在 `else if` 里也命中 —— 要看前面那个词。
- 症状没追到就 resolve —— 下一轮原样打回。
- heredoc 生成带 `\n` 的代码 —— 塌成真换行。

## 相关

- `pr-self-review` —— 哪些意见要修、怎么分档,推送前读自己的 diff。
- `mutation-verify` —— 变异检查的执行工具。
- `pr-review` —— 同一套眼光用在别人的 PR 上。
