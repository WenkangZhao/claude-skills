# 修评审意见,而不是把问题越修越多

不做分档(`pr-self-review`),不审别人的 PR(`pr-review`)。**这个技能只管:已经决定要修了,怎么改才不会带出新的。**

一次真实统计:五个 PR、18 轮评审,**11 轮里有"上一轮修复引入"的发现**。最严重的一次是插进 if 链里的一条语句把后面的 `else` 改嫁了——工具对所有普通调用都失效,而八条测试全绿、编译门全过。

---

## 第一屏:动手改之前,先产出四份东西

写进 scratchpad,**不是在脑子里过**。四份都写不出来,就还不该改代码。

### ① 轮次账 —— 这一轮该不该由我改代码

```bash
git diff --name-only <上一轮的提交>..HEAD
git log --oneline <本轮分支起点>..HEAD -- <这次要改的文件>   # 这个文件被改过几轮
```

- **同一个文件第三轮**:停。不要再改。写一段给评审:"前几次修在了错的位置,规则真正该待的地方是 X",然后重新分档。
- **这一轮的改动超过 ~50 行,或者动到了规则/引擎本身**:这已经不是修 comment,是重构。降级回 `pr-self-review` 全流程(依赖枚举、约束句、和评审重新划范围),不要用轻量流程。

> 实测:`OptimisationConfigRules.cs` 连续四轮被改,最后一轮 +249 行。没有任何机制拦住它——因为"同一文件三轮就冻结"这句话写在技能的**末尾**,而技能是在**动手前**读的。所以它现在是第一条,而且是一条命令。

### ② 表面清单 —— 同一个问题有几个地方要回答

**这是本次代价最大的一类(18 条发现)。** 输入形态表回答的是"一个地方会被哪些输入打到";这一步回答的是"这个问题有几个地方在回答它"。

```bash
grep -rn "<规则名/标识符/那句文案>" --include=*.cs --include=*.md .    # 两个仓库都要
```

一个行为规则在这类代码库里通常有 **三到六个家**:

| 表面 | 典型例子 |
|---|---|
| 写入口 | `CreateXxxCommand` |
| **第二个写入口** | `UpdateXxxCommand` —— 重写同一份数据,校验却只有一半 |
| 查询口 | `Describe` / `CanRun` —— 必须用**和拒绝时同一句话**回答 |
| 运行口 | 真正执行的那条路 |
| 第二个读者 | 桌面 ViewModel 和 DTO 映射读同一条记录 |
| 契约文档 | DTO 的 XML doc,以及它**兄弟成员**的 doc |
| 语料/手册 | cookbook part、schema description、file header |

**全部列出来,一个提交里一起改。** 漏掉任何一个,下一轮它就是新 comment。

> 实测:运行口加了拒绝、查询口没加 → 多一轮;SDK 结果里 DAS 天线不报频道、桌面表格还在报 → 多一轮;创建口校验了白名单、Update 口没校验 → 我自己 grep 出来才没多一轮。

### ③ 输入形态表 —— 退化行留空就是下一轮的 comment

列出**所有**能到达这段代码的形态,逐个手走,写下行号和结果。**下面这几行是预印的,必须填**:

```
形态                     走到哪    结果
空 / 一个都没有
恰好一个            ← 最高产:一个候选、一个频道、一个系统
全都一样 / 全都关掉
已经是目标状态了
被锁定 / 不可动
取消 / 中途失败
（再加这次改动特有的：策略 × 数量 × 命名空间 × 实体集合 的组合）
```

> 实测:这一批里有三轮完全是退化情形——"只有一个候选频道就不该叫选择"、"全向天线没有方向可言"、"DAS 天线根本没有自己的频道"。
>
> 还有一条更隐蔽的:**判定式不能用计数代替事实**。"有没有东西被钉住"(数 allow-list)代替了"这次要动的每个系统是不是都被钉住"——编译过、构建过、文本断言过、连围着它写的测试变异都过,整条绿色阶梯对这个缺陷是瞎的。**凡是写 count / length / Any / 存在性判断,先问一句:我数的这个东西,和我真正要保证的事实是同一件事吗?**

### ④ 包住编辑点的整个构造 + 出口 + 往返

- 把整条 if/else 链、整个方法、整个 using 块读完再动。**插入点紧跟着的下一条语句是什么?** 有没有 `else` / `catch` / `finally` 会改嫁给你。
- **出口**:我写进去的值,谁把它发出去?那条路径真的会执行到吗?(提示写进了错误信封不序列化的字段 = 用户什么也看不到)
- **往返**:我让对方回答的东西,回来的形状装得下吗?(把答案指到一个数组参数上,而表单合并回来的是标量 → 烘焙成空数组 → 死循环)

## 第二屏:改的时候

### 三条读法

1. **作者读"我改的那条路通了吗",评审读"我没改的那些路现在怎样"。** 回归永远在你没想到的那条路上。
2. **顺着数据往外读,直到它离开系统**,并且**同一个问题的每个表面必须给出同一个答案**(见 ②)。
3. **改措辞之前 grep 整个仓库**:你自己上一轮写的断言、别人的测试、cookbook,都可能钉着旧措辞。

### 绿色阶梯 —— 以及回帖前**必须**爬到哪一级

| 绿 | 证明了 | 没有证明 | 回这种严重度之前至少要到这级 |
|---|---|---|---|
| 解析 / py_compile | 能解析 | 任何行为 | — |
| 编译通过 | 类型能解析 | **控制流**(`else` 改嫁是合法 C#) | — |
| 构建通过 | 能产出程序集 | **测试会不会红** | — |
| 源码文本断言 | 某段文字在文件里 | **执行路径** | MINOR(且要说清这是文本断言) |
| 手走输入形态表 | 控制流 | 真实数据下的数值 | MAJOR |
| 变异检查 | 这条测试真钉住了这个修复 | 别的没被打破 | **CRITICAL / BLOCKER** |
| 真跑一遍 / 真执行的门 | 行为 | — | 写"已验证"三个字的唯一门槛 |

### 修复轮的测试契约(四条,全都是硬的)

1. **走产品入口**,不走你刚抽出来的 helper,也不自己 new 出中间值——否则生产那一半的接线没人钉。
2. **断言"到达的值",不要只断言"拒绝触发了"。** 这一批里最贵的教训:证明"请求不再被拒绝" ≠ 证明"频道真的落下去了"。两次都是评审替我发现的。
3. **变异检查,而且要按"别的作者会怎么写这个修复"去还原**,不是按你自己怎么写的去还原。锚点**从文件里粘贴**,不要凭记忆写(凭记忆写的锚点会让测试挂在自己的 assert 上,而不是挂在门上——一轮里发生过两次)。
4. **断言贴着被测的块**,不要整文件否定断言(会咬到你自己解释用的注释)。

**变异编译通过是常态,不是例外。** 可选参数(`IReadOnlyList<int> x = null`)删掉实参照样编译,结果静默变空。**构建绿在这里等于没验证。**

### 还要验证"验证器"本身

写了一个专门用来兜底的检查(桩保真检查、门、lint 规则)?**对它也做一次变异。**

> 实测:我写了个反射真 DLL、逐个比对桩里类型的检查,它绿了,我把它当"弱点已覆盖"写进了回帖。实际上解析器读出了类型却在传给探针前丢掉了——把 `Guid` 改成 `string` 它照样通过。**只有变异检查器本身才暴露出来。**

## 回帖:证据的级别和范围都不能虚

- **每个数字都必须来自在"已推送的那个 head"上跑过的命令**,并在回帖里点名是哪条命令。构建绿永远不是关于测试的证据。
- **范围也要写**:回帖里要有一行"这个规则涉及的每个表面/调用点:…"。只说"在 X 修好了"而同样的缺陷在 Y 还活着,是这一批里反复发生的事。
- **上一轮的说法复现不了,就在评审发现之前自己更正。** 我这次有两处:一处是"编译门通过"(机器上根本没有那个构建),一处是数字过期(42/42 → 50/50)。自己纠正的代价远小于被抓。
- **拒绝一条约定类意见时,第一次回复就把字节级证据摆上**(几个同目录文件有 BOM、loader 用的什么编码),不要拖到第二轮。
- **约定是按目录算的,不能跨仓库套用。** 同一条 BOM 意见:tool-engine 里 41 个文件 0 个有 BOM(该拒绝),iBuildNet 里 13 个文件 12 个有(该照做)。
- **评审引用了不存在的文件/代码,不等于论点错。** 引用和论点分开核。

## 三种"不算解决"

- **把缺陷写成注释里的"已知限制"。** 如果那句话描述的是用户会认为错的结果,它就是一条 finding。(我写过"One limit, stated rather than hidden…",那句话原文就是评审下一轮提的 CRITICAL。)
- **"历史遗留 / 超出范围"** —— 用之前先看工作项:这一批里有一条被连续两轮以这个理由关掉,第三轮才发现它就是工作项报的那个缺陷本身。
- **症状没追到就 resolve。** 只做了一半、或者选了三个方案之一的,留 active 并写清楚。不可争议的(措辞、大括号、评审指定的一条测试)修完直接 resolve,免得评审再点一遍。

## 每轮结束前的检查清单

```
git diff <上一轮的提交>..HEAD
```

1. **表面清单全打勾了吗?而且是在同一个提交里?**
2. **输入形态表的退化行填满了吗?**
3. 我插入的每一段,紧跟其后是什么?有 `else` / `catch` / `finally` 改嫁吗?
4. 判定式有没有用计数/长度/存在性代替真正的事实?
5. 这一轮加的每条测试:走产品入口了吗?断言的是到达的值吗?变异过吗?
6. 改了行为,**契约三件套**(规则代码 / DTO XML doc / cookbook part)都改了吗?**兄弟成员的 doc** 呢?
7. 用户可见的文案改了吗?五语资源跟上了吗?
8. 生成物/跨仓库的配对 PR(语料重发)要不要跟着动?合并顺序对吗?
9. 回帖里每句证据对应哪一级?范围行写了吗?
10. 要 resolve 的每一条,症状真的没了吗?

**一个 finding 一个提交**,提交信息写"行为变成了什么",不写 comment 编号——否则第 0 步那个 `git diff` 没有边界可用。

## 什么时候停下来改用写的

| 触发 | 下一步不是编辑,而是 |
|---|---|
| 同一个文件第三轮 | 给评审写"前几次修在错的位置,规则该在 X",重新分档 |
| 这一轮改动 > ~50 行 / 动到规则引擎 | 降级回 `pr-self-review` 全流程再推 |
| 严重度回升(MINOR → BLOCKER) | 把自己这几轮的 diff 当别人写的从头读一遍 |
| 没约定合并线 | 和评审约:BLOCKER/CRITICAL 清零,MAJOR 修或挂工作项,MINOR 作者裁量 |

## CI 在你修完之后变红,先分类再动手

1. **是不是已知抖动?** 本仓库有一类:`ReportEXTest` 约 25 条因 Measurement Templates 文件锁失败——不是你的改动,用 `ado_pr.py requeue <pr>` 重排。
2. **是不是你自己的测试?** 修复拿掉了某个"恰好成立"的东西,而旧测试正靠它通过(`Assert.Catch` 要求必须抛,你把越界修好了 → 红)。修复和它的测试要一起改。
3. **是不是 target 漂移?** 评审的意见可能写在更老的 merge base 上,或者 develop 中途合进来带了新 lint 规则。**每轮开始前先合一次 target,并读 target 新增了什么。**

## 工具坑(踩一次就够贵的)

- **多行代码用 Write 工具写,不要用 heredoc。** `\n` 会塌成真换行、引号会让 heredoc 提前结束——本次会话三次。
- **`%` 格式化含 `%` 的内容会炸**(body 里有 "95%")。用拼接。
- **管道的负面结果必须先证明工具跑过了。** `strings x.dll | grep -c Sym` 在没有 `strings` 的机器上静默输出 0,我据此断定"这个 DLL 没有那个符号"——错的,而且基于它的回帖也错了。
- **读退出码要直接读**,`grep -c` 无匹配退出 1,会把成功的构建显示成失败。
- 变异的具体执行、批量与还原安全,见 `mutation-verify`。

## 相关

- `pr-self-review` —— 分档、依赖枚举、约束句、维护类扫描、回复/resolve 策略。**本技能不重复这些,需要时按名引用。**
- `mutation-verify` —— 变异检查的执行工具与安全规则。
- `pr-review` —— 同一套眼光用在别人的 PR 上;严重度定义在 `pr-review/REVIEW.md`。
